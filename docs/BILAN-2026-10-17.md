## 1 · Ce qui est fait

### 1.1 Le socle (avant le 17 octobre)

- **Authentification et rôles** — cookies httpOnly + CSRF, OTP e-mail pour les
  professionnels, le patient par numéro sans code. 226 routes, chacune sous
  garde, avec un test qui parcourt la liste et refuse toute route non classée.
- **Chiffrement au niveau des champs** et journal d'audit.
- **i18n fr/en** maison, parité des clés (2766 clés de chaque côté).
- **Impression et export CSV** sur tous les écrans et tous les rôles, avec la
  protection contre l'injection de formules.

### 1.2 Le parcours de soin

- **Demande de rendez-vous** par le patient (six types de structures).
- **Orientation par l'accueil**, pointage de l'arrivée, épisode de soins.
- **Consultation par l'agent de santé communautaire** : constantes,
  diagnostic, ordonnance, alertes.
- **Consultation par le médecin depuis la visite** — agenda → dossier de la
  visite → « Ouvrir la consultation » → « Valider et signer ». Raccordé et
  vérifié de bout en bout le 17 octobre, avec quatre défauts corrigés (403 du
  médecin, fuite des consultations entre structures, validation toujours en
  400, deux sévérités de diagnostic refusées).
- **Laboratoire** — prescription, file du technicien, validation, libération
  des résultats au patient par le médecin.
- **Ordonnance signée → appel automatique aux pharmacies** du quartier.

### 1.3 Le circuit du médicament

- **P6-a** — machine à états de la commande, panier chiffré.
- **P6-b** — délivrance nominative : partielle, substituée ou refusée, motif
  obligatoire, jamais plus que le prescrit.
- **Paiement** — passerelle ChapChap et encaissement au comptoir.

### 1.4 Les décisions tranchées

- **D2** — la téléconsultation est de la vraie visioconférence.
- **D4** — si l'assureur rejette, le patient paie, avec une preuve imprimable
  du refus ; les montants d'origine ne sont pas remis à zéro.
- Le médecin reçoit les épisodes et les alertes de l'hôpital, pas l'admission
  ni les identités.
- Prescrire avant les résultats d'analyse reste permis : avertissement, pas
  verrou.

### 1.5 La refonte UI/UX — **terminée sur tous les écrans existants**

**Phase 1 (PR #4)**
- Socle SCSS : jetons de couleur, ombres, focus, gouttière fluide, courbe
  d'animation commune ; composants Material alignés.
- Sept lots d'écrans : messagerie, ordonnances, stocks, consultations,
  référencements, tableaux de bord, espaces patient, agent de santé, hôpital,

- Page d'accueil et pages d'authentification (connexion, code PIN,

- **Cinq pages publiques** : Confidentialité, Conditions d'utilisation

  À propos.
- **Navigation publique unifiée** (menu mobile, onglet actif, ancres).
- **Dépendances** : 6 failles critiques et 42 élevées → 0.

**Phase 2 (PR #5) — les 27 écrans arrivés avec `develop`**

## 3 · Installer le projet sur un autre PC

### 3.1 Ce qu'il faut installer d'abord

| Outil | Version | Pourquoi |
|---|---|---|
| **Git** | récente | récupérer le code (Git Bash sert aussi aux scripts de sauvegarde) |
| **Node.js** | **24.x** | la même version que la CI |
| **PostgreSQL** | 16 | la base de données |
| Redis | optionnel | seulement si `REDIS_URL` est renseigné |

### 3.2 Récupérer le code (une seule fois)

```powershell
cd C:\Pricemou
git clone https://github.com/Cecedjibrilpricemou/baobaoheath-platforme.git
cd baobaoheath-platforme
git switch develop
```

### 3.3 Le fichier `.env` — **à transporter à la main**

Le fichier `apps/api/.env` **n'est pas dans Git**, et c'est voulu : il contient
les mots de passe et les clés.

1. Sur l'ancien PC, copier `apps/api/.env` sur une clé USB ou par un canal
   sûr. **Jamais** par e-mail en clair, jamais dans le dépôt.
2. Sur le nouveau PC, le déposer dans `apps/api/.env`.
3. Si on part de zéro, partir du modèle : copier `apps/api/.env.example` vers
   `apps/api/.env` et remplir chaque valeur.

> ⚠️ **`DB_ENCRYPTION_KEY` doit être identique partout où la même base est
> lue.** Avec une autre clé, les champs chiffrés (noms, téléphones,
> diagnostics…) deviennent illisibles. Si la base vient de l'ancien PC, sa
> clé vient avec elle.

Variables à vérifier : `DATABASE_URL` (adresse, port et mot de passe de la
base du nouveau PC), `JWT_SECRET`, `JWT_REFRESH_SECRET`, `DB_ENCRYPTION_KEY`,
`GMAIL_USER` / `GMAIL_APP_PASSWORD` (envoi du code PIN), `CHAPCHAP_*`
(paiement), `ALLOWED_ORIGINS` et `FRONTEND_URL`.

### 3.4 Installer les dépendances

À la racine du projet :

```powershell
npx npm@11 ci
```

> En cas d'erreur `EPERM` : un fichier est utilisé par un autre programme.
> Arrêter tout `ng serve`, fermer VS Code, relancer.

### 3.5 Préparer la base de données

**Option 1 — reprendre les données de l'ancien PC** (recommandé)

La sauvegarde est compressée et **chiffrée** : il faut choisir une phrase de
passe (`BACKUP_ENCRYPTION_KEY`) et la garder pour la restauration. Les
scripts lisent `DATABASE_URL` dans l'environnement ; il faut `pg_dump` /
`psql` dans le PATH (ou le conteneur Docker `baobao_db`) et `openssl` (fourni
avec Git Bash).

Sur l'ancien PC, dans **Git Bash**, à la racine du projet :
```bash
export DATABASE_URL='postgresql://UTILISATEUR:MOT_DE_PASSE@127.0.0.1:5433/baobaoheath_db'
BACKUP_ENCRYPTION_KEY='une-phrase-de-passe' npm run backup:db
```
Le fichier apparaît dans `backups/` (par exemple
`backups/baobaoheath_20261017T220000Z.sql.gz.enc`). Le copier sur le nouveau
PC, au même endroit, puis dans Git Bash :
```bash
export DATABASE_URL='postgresql://UTILISATEUR:MOT_DE_PASSE@127.0.0.1:5433/baobaoheath_db'
BACKUP_ENCRYPTION_KEY='une-phrase-de-passe' bash scripts/restore-db.sh backups/LE_FICHIER.sql.gz.enc
```
⚠️ La restauration **écrase** la base visée : vérifier `DATABASE_URL` avant.
La même `DB_ENCRYPTION_KEY` est indispensable dans `.env` (voir 3.3).

**Option 2 — base neuve**

Créer une base vide dans PostgreSQL, renseigner `DATABASE_URL`, puis :

```powershell
cd apps\api
npx --no-install prisma generate --config prisma.config.ts
npx --no-install prisma migrate deploy --config prisma.config.ts
npm run prisma:seed
npm run prisma:seed:demo
cd ..\..
```

> `--no-install` empêche `npx` de télécharger une autre version de Prisma.
> Ignorer le message « Update available … 8.0.0-rc » : on reste en 7.10.1.

Dans les deux cas, toujours lancer `prisma generate` après une installation.

### 3.6 Lancer l'application

À la racine :

```powershell
npm run dev
```

Cela lance l'API et le front ensemble. Le front s'ouvre sur
`http://localhost:4200`. Pour tester depuis un téléphone du même réseau :
`npm run dev:lan`.

Le guide de démonstration (comptes et mots de passe) reste **hors du dépôt**,
à dessein : il se transporte à la main, comme le `.env`.

### 3.7 Se mettre à jour les jours suivants

```powershell
cd C:\Pricemou\baobaoheath-platforme
git switch develop
git pull origin develop
```

Puis, **seulement si** le `pull` a modifié `package-lock.json` :
```powershell
npx npm@11 ci
```

Et **seulement si** le `pull` a ajouté un dossier dans
`apps/api/prisma/migrations` :
```powershell
cd apps\api
npx --no-install prisma generate --config prisma.config.ts
npx --no-install prisma migrate deploy --config prisma.config.ts
cd ..\..
```

Pour savoir ce qu'un `pull` a changé : la liste des fichiers s'affiche à la fin
de la commande.

### 3.8 Vérifier que tout va bien

```powershell
npm run build:web
cd apps\api
npm test
cd ..\..
```

Les tests de l'API demandent une base PostgreSQL de test : ils sont de toute
façon rejoués par la CI à chaque PR.

## 4 · Les règles de travail qu'on garde

- **API d'abord, front ensuite, dans le même bloc.**
- **Étape par étape, pas tout en un.**
- Les identifiants et les clés restent **hors du dépôt Git** : un mot de passe
  n'a pas sa place dans l'historique. `.env` se transporte à la main.
- `DB_ENCRYPTION_KEY` doit être **identique partout où la même base est lue**.
- L'**assureur ne voit jamais de donnée médicale** : des agrégats seulement.
- La **pharmacie ne voit que le nom du patient et les produits**.
- Les **feuilles imprimées** ne portent ni le code de retrait de l'ordonnance,
  ni le numéro complet de la pièce d'identité, ni les valeurs d'analyse, ni les
  produits d'une vente.
- Toute migration se **prouve sur une base jetable** : on regarde chaque garde
  **refuser**, puis accepter.
- Chaque correctif est **saboté** avant d'être cru.
- Refonte UI : **SCSS uniquement** pour le visuel, variables `--bb-*`,
  marqueur `// ✦ Refonte UI`, clair **et** sombre, contraste AA vérifié.
